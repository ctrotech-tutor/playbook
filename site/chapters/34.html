Chapter 34

How forms send data

Start with the request, then choose the controls.

4 MIN READ + PRACTICESOURCE-LINKED PRACTICEOCTOBER 2026
By the end of this chapter
  • Distinguish name from id
  • Explain a form request without inventing a backend
  • Inspect repeated entries and submitter participation

A form constructs an entry list from eligible controls and submits it according to its action, method and encoding rules. A visible input without a name usually does not contribute the expected name-value entry. An id connects labels and references; it is not the submission key.

GET commonly expresses retrieval by placing the encoded query in the URL. POST sends a request body under the selected encoding. Neither method provides encryption by itself. Use HTTPS for transport protection where appropriate and implement the server's validation, permissions and storage handling.

Make the simple path work

A search form can submit without JavaScript. Build that path first when the service supports it. Scripts can enhance the experience without becoming the only way to reach the result.

Controls outside a form can be associated through a form attribute when their element supports it. Avoid relying on visual proximity as a submission relationship. Check actual submitted entries, including unchecked controls, disabled fields and the button used to submit. A browser preview without a backend cannot prove a successful application workflow.

Predict the entry list

For an ordinary named text input, the name becomes the entry key and the current value becomes its value. A disabled control is omitted. An unchecked checkbox or radio button is omitted too; it does not automatically send a false value. A readonly text input can still contribute an entry. Repeated names can produce multiple entries, so do not assume that every form is a one-value-per-key object.

Give the server a deliberate interpretation for missing and repeated entries. Do not trust a disabled field, a hidden field or a client-side constraint to enforce a permission. Someone can construct a request without using your interface.

Observe entries instead of guessing from the controls

For a form with two checked controls both named topic, new FormData(form).getAll("topic") reads both entries. Turning the entries into an ordinary one-value object can lose that relationship. Output elements are associated with forms but do not submit their result values merely because they have names.

new FormData(form, submitButton) includes that eligible submitter's entry; constructing it without a submitter omits the submit buttons. A formdata event is fired while constructing the list, allowing a handler to inspect or amend its FormData. This is not the cancelable submit event and does not itself send a request.

A named file input with no selected file still has a defined empty File entry, rather than behaving exactly like an unchecked checkbox. A hidden _charset_ field has special encoding-value behavior. A supporting text control with dirname="reader.dir" can contribute an additional direction entry whose value is ltr or rtl.

The missing and invalid method defaults are GET; the usual missing or invalid enctype default is application/x-www-form-urlencoded. method="dialog" has a different purpose: inside a dialog it can close that dialog rather than send an application request. Chapter 41 compares the submission paths.

The FormData constructor and its entry accessors are defined by the XMLHttpRequest Standard; HTML defines how a form constructs its entries. During native construction, trying to construct another FormData from the same form inside its formdata listener hits the construction guard and throws InvalidStateError. Amend the supplied event.formData instead of starting that construction again.

The example

HTML / example 34
<form action="catalogue.html" method="get">
  <label for="query">Search the catalogue</label>
  <input id="query" name="q" type="search">
  <button type="submit">Search</button>
</form>

The query key is q because that is the name. A real catalogue endpoint must read the query and return results; a static catalogue file does not implement that search service automatically.

A mistake to watch forAssuming that giving a control an id is enough to send its value under that key.

Your turn

Check your understanding

Why might a filled input appear on screen but be absent from the submitted entry list? Will new FormData(form) automatically include every submit button?

Read the explained answer

It may lack a name, be disabled, be outside the relevant form without an association, or fall under another exclusion rule. Inspect the actual control state and form data rather than the visual layout. No. Buttons are excluded unless the relevant submitter is supplied to entry-list construction. Repeated names remain separate entries; inspect them with getAll when the data model expects several values.
