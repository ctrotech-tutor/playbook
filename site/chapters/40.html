Chapter 40

Validation people can recover from

An error message should help someone finish the task.

4 MIN READ + PRACTICESOURCE-LINKED PRACTICEOCTOBER 2026
By the end of this chapter
  • Apply state-specific constraints
  • Design and test the correction path
  • Choose output, progress and meter without inventing a running service

Native constraints include required, appropriate type rules and state-specific min, max, step, pattern and length restrictions. Their applicability differs by input state. A constraint in the wrong state may do nothing.

Constraint validation helps guide ordinary interaction. It does not secure a request. A server must validate the submitted data, enforce permissions and return useful errors even when JavaScript or browser validation has been bypassed.

Keep the correction near the field

When application validation finds an error, identify the field and explain how to fix it. Preserve the submitted non-sensitive values when appropriate. Connect useful error text with aria-describedby and update aria-invalid when the application knows the value is invalid. Do not mark a field invalid before there is a reason to do so.

setCustomValidity can add an application message to supporting controls; a nonempty message keeps the control invalid until cleared. A mismatch between custom validity and visible errors can trap someone in a form. Test correction, not just failure. Native error UI varies between browsers, so do not base instructions on one screenshot.

Know what the constraints actually measure

Pattern matching uses the JavaScript Unicode-sets v mode and checks the whole nonempty value, not a substring. Do not include slash delimiters. An invalid pattern has no compiled expression, so testing one successful string is not enough to prove that the intended rule is enforced. required handles the otherwise-empty value separately.

Length constraints use the defined API value length, measured in UTF-16 code units rather than user-perceived characters. Their tooShort and tooLong conditions have user-edit and dirty-value requirements; a script assignment is not an equivalent way to test all typing constraints. Test real edits and the correction path.

checkValidity() checks applicable constraints and can fire invalid events on failing controls. reportValidity() additionally uses the browser's reporting behavior. The invalid event does not bubble like an ordinary input event; a form-level listener can use capture when it needs those events. Keep error messages meaningful instead of promising identical native popup text everywhere.

Results and gauges are not extra submission fields

output represents a calculation or action result. For example, <output for="copies" name="copyResult">2 copies selected</output> relates a result to the copies input from Chapter 37. Its for value is a unique-token list of element ids in the same tree, not the label element's one-control rule. An output value is not submitted merely because name is present, and it is barred from constraint validation.

progress represents task completion: <label for="catalogue-progress">Records indexed</label><progress id="catalogue-progress" max="10" value="3">3 of 10</progress> has a determinate value. Remove value for indeterminate progress. The default maximum is 1; an explicit maximum must be positive, and a determinate value must be within the permitted range.

meter is a measurement within a known range, not a task's completion. <label for="seats">Seats occupied</label><meter id="seats" min="0" max="20" value="12">12 of 20 seats</meter> expresses a gauge. Its value is required; low, high and optimum are optional range points with ordering constraints. Give a visible value and units where useful, rather than relying on color alone. None of these elements implements a calculation, upload, indexing job or occupancy sensor by itself.

The example

HTML / example 40
<label for="card-number">Membership number</label>
<input id="card-number" name="cardNumber" inputmode="numeric"
       pattern="[0-9]{6}" aria-describedby="card-format" required>
<p id="card-format">Enter the six digits printed on your card.</p>

The pattern applies to this text-state input. inputmode is a keyboard hint. The six-digit rule is fictional teaching policy and needs a matching server-side rule in a real service.

A mistake to watch forAdding a pattern without visible formatting guidance, or showing a generic Something went wrong message for a correctable field error.

Your turn

Check your understanding

After setting a custom validity message, a script sees the corrected value. What must it do to let the field become valid? Should seats occupied out of 20 be represented as task progress?

Read the explained answer

Clear the custom message with setCustomValidity("") when the custom condition passes. Other native constraints may still apply, so inspect validity rather than assuming clearing one message proves every rule passed. No. That is a bounded measurement suited to meter, not progress. A computed result can use output, but its value is not automatically a submitted form entry.
