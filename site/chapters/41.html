Chapter 41

Submission and server boundaries

A finished form includes what happens after the request.

3 MIN READ + PRACTICESOURCE-LINKED PRACTICEOCTOBER 2026
By the end of this chapter
  • Choose an encoding for the actual data
  • Separate a static form interface from its service
  • Predict submitter exceptions and validation-bypass behavior

Form submission produces an entry list and a request under defined rules. application/x-www-form-urlencoded is the common default encoding. File uploads through a conventional POST form need multipart/form-data. Do not choose text/plain as a general production data format merely because it looks readable.

A submit button can override supported submission attributes for that submission. The button used can also contribute its own name and value. Test these details when one form supports several actions.

Protect and explain the result

Use server-side validation, appropriate authorization and protections suited to the application, including CSRF defenses where the authentication and request model need them. HTTPS protects transport; it does not decide whether the requester may change a record.

A successful HTTP response is not necessarily a successful business operation. Show whether the application accepted, rejected or queued the action, and explain the next step. Handle retries and duplicate submissions according to the service's data model. Static hosting serves the interface; a working submission service needs a separately implemented handler.

Choose the submission path deliberately

Calling form.requestSubmit() runs the applicable constraint validation and, if submission proceeds, dispatches a submit event. Calling form.submit() directly bypasses that validation step and does not fire the submit event. Do not treat those methods as interchangeable shortcuts. Pass the intended submit button to requestSubmit() when its name, value or overrides matter.

For a multipart upload sent with fetch and FormData, let the browser generate the Content-Type boundary rather than hand-writing a bare multipart header. Read the service's expected request format and response contract before adapting a markup-only example. Use fictional data in local demonstrations. GET query values appear in the URL, and switching to POST does not replace HTTPS or careful logging and storage policies.

Defaults, overrides and exceptions belong in the contract

The accepted authoring value of accept-charset is UTF-8, matched case-insensitively. This is not a menu of legacy encodings to copy into a new form. Submission overrides belong to an eligible submit button; a hidden text field with the same spelling does not override the method or endpoint.

requestSubmit(submitter) throws TypeError if the argument is not a submit button and NotFoundError if its form owner is different. Omitting the argument does not select every named button. A control named or identified as submit can also mask the form's submit method through named-property behavior; avoid such collisions rather than silently switching to a validation-bypassing path.

novalidate on a form and formnovalidate on an applicable submit button skip the interactive validation stage; they do not remove server-side obligations. A canceled submit event prevents that submission, while a formdata handler can amend the entry list. Constructing a FormData object alone sends nothing.

For a dialog form, method="dialog" closes the containing dialog and can set its return value from the submitter instead of issuing the usual request. Keep that separate from a form advertised as saving an application. For real native requests, inspect the method, target, encoded entries and response; an ordinary local fixture is evidence of browser behavior, not a deployed business service.

The example

<form action="/applications" method="post" enctype="multipart/form-data">
  <label for="proof">Address document</label>
  <input id="proof" name="proof" type="file" required>
  <button type="submit" name="action" value="apply">Send application</button>
</form>

A mistake to watch forClaiming a contact or application form works because the browser renders the fields and button.

Your turn

Check your understanding

What else is required before this form can be advertised as accepting real applications? What happens if requestSubmit receives a submit button owned by another form?

Read the explained answer

A working endpoint, validated and authorized handling, appropriate upload limits and storage controls, a clear privacy policy, and tested user-visible results for success, error and retry cases. Confirm deployment and transport behavior too. It throws NotFoundError. A non-submit button produces TypeError. Handle the intended form/submitter relationship rather than treating either method as a generic submit shortcut.
