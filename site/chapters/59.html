Chapter 59

HTML and rendering

Default styles are a starting point, not the meaning.

2 MIN READ + PRACTICESOURCE-LINKED PRACTICEOCTOBER 2026
By the end of this chapter
  • Distinguish default appearance from meaning
  • Keep source and interaction order understandable
  • Keep actual navigation destinations and reading order coherent

Browsers have default rendering rules and styles. A heading often appears bold and large; an anchor often appears underlined. Those defaults make an unstyled document usable, but they do not define every semantic or accessibility behavior.

Changing display can alter layout without changing the element's underlying HTML definition. It can also interact with accessibility mappings and implementation quirks. Test the actual result rather than assuming a CSS property is semantically harmless everywhere.

Keep reading order deliberate

Layout can visually reorder items while the DOM order stays the same. A keyboard or screen reader may encounter a sequence unlike the visual arrangement. Put the logical order in HTML and use layout to adapt it without creating competing stories.

Use HTML attributes with their intended behavior rather than recreating them through presentation alone. CSS hiding, hidden and inert have different consequences. Contrast, focus visibility, reflow and zoom are also part of the usable page, even though their implementation often lives in CSS.

Visual position does not rewrite source order

Flex/grid order can change the visual sequence without rewriting the DOM's ordinary sequence. Do not repair a visual mismatch with a chain of positive tabindex values. Fix the meaningful source order, then check both the layout and the actual keyboard/reading experience.

Browser default styles are rendering guidance with implementation variation. Removing a default outline, suppressing an underline or forcing colours can remove a useful affordance. Test forced-colour settings, zoom and narrow layouts with actual content.

A computed CSS value does not prove an accessible-name or role mapping. HTML-AAM and the accessible-name computation address different questions from a screenshot. Display changes and native control styling need implementation and assistive-technology evidence beyond the semantic source definition.

The example

HTML / example 59
<article>
  <h1>Visit the fictional reading room</h1>
  <p>These are teaching values, not a real service timetable.</p>
  <a href="#example-hours">Read the example hours</a>
  <section id="example-hours" aria-labelledby="hours-heading">
    <h2 id="hours-heading">Example opening hours</h2>
    <p>Tuesday to Saturday, <time datetime="09:00">09:00</time>
       to <time datetime="17:00">17:00</time>.</p>
  </section>
</article>

The link now reaches actual in-document teaching content. The DOM gives the context before the destination and remains useful without layout. These fictional hours are not a claim about a real library.

A mistake to watch forChoosing an element because its browser default margin looks right, then compensating for the wrong semantics with ARIA.
