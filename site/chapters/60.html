Chapter 60

Where the wider APIs begin

Know the boundary before calling the reference exhaustive.

5 MIN READ + PRACTICESOURCE-LINKED PRACTICEOCTOBER 2026
By the end of this chapter
  • Identify wider API responsibilities
  • Keep API integration separate from member-level completeness
  • Execute storage recovery and a bounded worker with failure paths

The HTML Standard includes more than markup. It defines navigation and history behavior, messaging, workers, worklets, storage, event loops and many interfaces. A language guide can introduce their integration, but a named-interface list does not document every member or algorithm.

localStorage is synchronous, origin-scoped storage with its own access and failure behavior. It is not a suitable place for secrets simply because it is local. Workers run script in a different execution environment, not a second DOM you can manipulate directly. Messaging needs explicit origin and data validation where relevant.

Treat integration as a design decision

A history update needs a corresponding content and navigation strategy. A cross-document message needs an expected sender and validated payload. A background task needs cancellation and failure handling. These responsibilities do not disappear because the API call is short.

What the catalogue actually contains

The foundation catalogue retains 166 named interface discovery routes. The expanded declaration register separately records 314 named WebIDL declaration owners and 1,574 direct member declarations in the captured source. Owners include more than interfaces, and direct declarations do not expand every inherited member. These are different inventories, not competing counts of the same thing.

Use the declaration register for signatures and links to definitions. A declaration alone does not explain an algorithm, an exception, an event sequence or a security boundary. Some member links deliberately fall back to their owning definition and are labelled accordingly. Whole-Standard behavioral coverage, imported cross-specification APIs and independent review remain open.

Storage can fail. Access may be restricted by the document's origin or browser policy, and writes can fail when storage limits are reached. Keep the page usable when a preference cannot be saved. Do not assume that a successful write is a durable backup or that any script running in the same origin is barred from reading the stored data.

Storage methods have different contracts

Storage values are strings. getItem returns null when the key is absent; key(index) can return null; ordering is not a portable insertion-order guarantee. setItem can throw QuotaExceededError, and obtaining storage for an ineligible origin or under policy can throw SecurityError. localStorage and sessionStorage have different lifetime/partition rules. Use removeItem for your own key instead of clear when unrelated same-origin settings must remain.

A storage event is delivered to the relevant other documents, not as a notification to the writing document itself. A no-change write is not a new-value event. Same-origin access is not a user-account permission boundary, and persistence can be cleared or restricted by browser policy.

History and messages need more than a method call

pushState and replaceState do not by themselves load a new view. Their serializable state and same-origin URL constraints can produce DataCloneError or SecurityError. Read popstate state and restoration needs when designing traversal. Newer Navigation APIs require separate lifecycle/compatibility work.

postMessage serializes data using the defined structured-clone rules. An uncloneable function can produce DataCloneError. Use a specific target origin for normal cross-document delivery, then validate event.origin, event.source and the payload shape at the receiver. A wildcard or a familiar-looking message string is not sender authentication. Transferring an ArrayBuffer changes ownership and detaches it under the transfer rules; it is not just copying JSON.

MessageChannel/MessagePort and BroadcastChannel have different addressing and lifecycle contracts. Start or close ports/channels as appropriate, handle messageerror where relevant and avoid assuming that a channel name is a secret permission token.

Worker and scheduling scope remains explicit

A dedicated worker has its own global scope, not document access. Construction/loading, CSP, origin restrictions, serialization, errors and termination all matter. The supplied worker is a tiny bounded calculation, not a performance benchmark or shared/service-worker lifecycle demonstration.

A timeout is a minimum-delay scheduling request, not an exact alarm. Nested timers have the defined clamping rules, and background scheduling can differ. requestAnimationFrame runs under rendering opportunities; it can be paused or throttled. The full owner/member register, worklets, shared/service workers and all event-loop/timing/navigation algorithms remain open, not silently excluded.

The example

HTML + JavaScript / example 60
<form id="example-preference">
  <label for="example-view">Example view preference</label>
  <select id="example-view" name="view">
    <option value="comfortable">Comfortable</option>
    <option value="compact">Compact</option>
  </select>
  <button type="submit" disabled>Store example preference</button>
  <button type="button" id="remove-preference" disabled>Remove stored preference</button>
</form>
<p id="preference-result" role="status">No storage result yet.</p>
<button type="button" id="run-worker" disabled>Run background sum</button>
<p id="worker-result" role="status">No calculation requested.</p>
<p><a id="worker-source" href="../assets/worker-demo.js" download="worker-demo.js">Download the supplied worker source</a></p>
<script>
  const form = document.getElementById("example-preference");
  const choice = document.getElementById("example-view");
  const note = document.getElementById("preference-result");
  const key = "ctrotech.teaching.view";
  try {
    const stored = localStorage.getItem(key);
    if (stored === "compact" || stored === "comfortable") {
      choice.value = stored;
      note.textContent = "Stored example preference restored.";
    } else {
      note.textContent = "No recognized stored preference; choose a local value.";
    }
  } catch {
    note.textContent = "Storage unavailable; the selection still works locally.";
  }
  form.addEventListener("submit", event => {
    event.preventDefault();
    try {
      localStorage.setItem(key, choice.value);
      note.textContent = "Example preference stored in this browser.";
    } catch {
      note.textContent = "Not stored; the selection still works locally.";
    }
  });
  const remove = document.getElementById("remove-preference");
  remove.addEventListener("click", () => {
    try {
      localStorage.removeItem(key);
      note.textContent = "The example's stored preference was removed.";
    } catch {
      note.textContent = "Storage unavailable; no removal confirmed.";
    }
  });
  form.querySelector("button[type=submit]").disabled = false;
  remove.disabled = false;
  const run = document.getElementById("run-worker");
  const workerNote = document.getElementById("worker-result");
  run.addEventListener("click", () => {
    run.disabled = true;
    workerNote.textContent = "Calculating the teaching sum.";
    let worker;
    let finished = false;
    let timer;
    const finish = text => {
      if (finished) return;
      finished = true;
      clearTimeout(timer);
      workerNote.textContent = text;
      if (worker) worker.terminate();
      run.disabled = false;
    };
    timer = setTimeout(() => finish("Calculation timed out; try again."), 5000);
    try {
      worker = new Worker(document.getElementById("worker-source").href);
      worker.addEventListener("message", event => {
        const data = event.data;
        finish(data && data.kind === "sum" && Number.isFinite(data.total)
          ? "Background sum: " + data.total
          : "The worker returned an unusable result.");
      }, { once: true });
      worker.addEventListener("error", event => {
        event.preventDefault();
        finish("Background calculation unavailable.");
      }, { once: true });
      worker.addEventListener("messageerror", () => finish("Worker message could not be read."), { once: true });
      worker.postMessage([2, 3, 5]);
    } catch {
      finish("Background calculation unavailable.");
    }
  });
  run.disabled = false;
</script>

The storage controls restore, store and remove only a namespaced teaching key, with truthful failure messages. The supplied worker validates a short finite-number payload, computes 10 and is terminated after completion, reported failure or the stated five-second teaching timeout. Its URL comes from an actual source link, so the compiled hashed asset stays resolvable. The editor restricts storage/workers; use the standalone example for successful paths. This is not a durable backup, a view-layout implementation or an exhaustive worker application.

A mistake to watch forCalling a reference complete because every interface name appears somewhere in it.

Your turn

Check your understanding

Why does the example catch a storage failure rather than assuming localStorage is always writable? Does a storage event notify the writing document of its own setItem call?

Read the explained answer

Access restrictions, browser settings and storage failures can prevent writing. A preference control should remain usable and explain the actual result. Do not report a successful save when the write failed. No. Use an explicit local update and the specified events for other documents. Transfer, history and worker methods also have their own serialization, origin and lifecycle constraints.
