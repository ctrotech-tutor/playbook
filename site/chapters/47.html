Chapter 47

Custom data and structured data

Store page-specific values without inventing semantics.

3 MIN READ + PRACTICESOURCE-LINKED PRACTICEOCTOBER 2026
By the end of this chapter
  • Read custom data with explicit type handling
  • Distinguish page-specific data from public structured annotations
  • Validate dataset values and distinguish assignments from deletion

data-* attributes store page-specific data where no more appropriate attribute fits. Scripts can access them through dataset with the defined name conversion. Values are strings; a value such as "false" is not automatically a false boolean.

Custom data is visible in the document. Do not place credentials or trusted authorization decisions there. A visitor can inspect and change it. Do not use a data attribute as a substitute for a real href, label or disabled state when the platform already defines one.

Microdata serves a different purpose

itemscope, itemtype, itemprop, itemid and itemref participate in microdata. A vocabulary supplies meaning to properties; arbitrary names do not create a recognized public schema. Search and other consumers have their own supported formats and policies.

Keep visible content and structured annotations consistent. Do not claim that adding structured data guarantees a search result treatment. Choose a supported vocabulary and validate both its syntax and the content it represents using the relevant consumer's current documentation.

Conversion and deletion have defined rules

A dash followed by an ASCII lowercase letter becomes an uppercase letter in dataset: data-book-id becomes bookId. Other permitted characters are not all transformed by that same rule. Assigning null writes the string "null"; delete removes an entry. Assigning through a key with a dash followed by an ASCII lowercase letter, such as dataset["loan-days"], throws SyntaxError rather than acting like dataset.loanDays.

A test with in can see properties on a prototype as well as this map's own entries. Use a suitable own-property check where that distinction matters. Convert only the format the application actually accepts; Number("") becoming zero is not proof that an empty quantity is valid.

Microdata needs a real item model

itemscope starts an item, itemtype identifies vocabulary types, and itemprop names properties. itemid supplies a global item identifier under the vocabulary and authoring rules; itemref can refer to additional property-bearing elements by id in the same tree. It is not a general DOM ownership or permission relationship.

A Book item can use name for its visible title and an author property containing a nested Person item with its own name. Do not invent a credential, review or affiliation simply to fill a structured-data property. Element-specific value rules matter: meta uses content, time can use datetime, and URL-bearing elements have their own value extraction. A parsed graph alone does not guarantee a search treatment.

The example

HTML + JavaScript / example 47
<article id="book-record" data-book-id="LIB-204" data-copy-count="3">
  <h2>Local histories</h2>
  <p id="copy-note">This is a fictional record.</p>
</article>
<script>
  const record = document.getElementById("book-record");
  const rawCount = record.dataset.copyCount;
  const count = Number(rawCount);
  const valid = /^[0-9]+$/.test(rawCount) && Number.isSafeInteger(count);
  document.getElementById("copy-note").textContent = valid
    ? count + " copies listed in this fictional record."
    : "No usable quantity in this fictional record.";
</script>

The record now demonstrates string-to-number validation and a real text update instead of an unimplemented Save button. It deliberately rejects malformed or unsafe numeric values and never treats this local record as an authorization decision or real stock availability.

A mistake to watch forAdding data-disabled="true" and expecting native disabled behavior.

Your turn

Check your understanding

What JavaScript type do you get from element.dataset.count when the source has data-count="3"? What does assigning null to a dataset entry do?

Read the explained answer

You get the string "3". Convert and validate it deliberately if your application needs a number. Do not trust the value merely because it appeared in your own initial markup. It stores the string "null". Use delete to remove the entry, and validate any parsed value deliberately rather than treating stored strings as trusted typed data.
