Chapter 45

Focus, editing and dragging

An interaction needs a path that does not depend on a pointer.

3 MIN READ + PRACTICESOURCE-LINKED PRACTICEOCTOBER 2026
By the end of this chapter
  • Explain sequential and programmatic focus
  • Provide a non-drag path for important actions
  • Test actual reordering and focus rather than a decorative button

Focusable and sequentially focusable are related but distinct. tabindex="0" can place an otherwise suitable element in sequential focus order. tabindex="-1" commonly allows programmatic focus without adding an ordinary tab stop. Positive tabindex values create a separate ordering problem and are usually best avoided.

contenteditable enables editing under its defined states. It does not provide a complete rich-text editor, accessible toolbar, sanitation pipeline or save system. Editing behavior and supported input methods need real-device testing.

Offer alternatives to dragging

draggable participates in the drag-and-drop model. A drag gesture should not be the only way to perform an important operation. Provide buttons or another keyboard-usable mechanism for moving an item, and keep the outcome understandable.

Use focus to support a task, not to surprise someone whenever content changes. When removing a focused item, decide where focus goes next. Avoid trapping focus in a non-modal widget. Mobile input, speech control and assistive technology can expose assumptions that mouse-only testing misses.

Editing and dragging use enumerated states

contenteditable accepts true, an empty true value, false and plaintext-only; missing or invalid values inherit. isContentEditable reports the resulting editing condition, not merely the stored attribute spelling. Plaintext-only is not an HTML sanitizer or a persistent storage service.

draggable is enumerated, not boolean. Its true and false values differ from missing or invalid Auto, under which images, links and selections have their own default drag behavior. Do not write draggable="false" and assume it follows the boolean-attribute rule from disabled.

During drag-and-drop, DataTransfer has mode and phase restrictions. Write the intended data during dragstart, allow an intended drop through the relevant dragover handling, and read/validate the data in the allowed drop phase. Treat incoming text or HTML as untrusted. A synthetic DragEvent or constructed DataTransfer is not proof that native pointer, touch or assistive-technology dragging works.

The reordering controls are both a keyboard path and a single-pointer non-drag path. Those are separate accessibility considerations: keyboard operation alone is not the entire dragging-movements requirement. Test the actual pointer and keyboard controls, focus after a move and the readable result.

The example

HTML + JavaScript / example 45
<section aria-labelledby="list-title">
  <h2 id="list-title" tabindex="-1">Your fictional reading list</h2>
  <ol id="reading-list">
    <li tabindex="-1"><span>Local histories</span>
      <button type="button" data-shift="-1" disabled>Move up</button>
      <button type="button" data-shift="1" disabled>Move down</button></li>
    <li tabindex="-1"><span>Poetry</span>
      <button type="button" data-shift="-1" disabled>Move up</button>
      <button type="button" data-shift="1" disabled>Move down</button></li>
    <li tabindex="-1"><span>Fiction</span>
      <button type="button" data-shift="-1" disabled>Move up</button>
      <button type="button" data-shift="1" disabled>Move down</button></li>
  </ol>
  <p id="move-status" role="status">Changes stay in this page only.</p>
</section>
<script>
  const list = document.getElementById("reading-list");
  const status = document.getElementById("move-status");
  function updateMoves() {
    [...list.children].forEach((item, index, items) => {
      const title = item.querySelector("span").textContent;
      item.querySelectorAll("button").forEach(button => {
        const up = button.dataset.shift === "-1";
        button.disabled = up ? index === 0 : index === items.length - 1;
        button.setAttribute("aria-label", (up ? "Move up: " : "Move down: ") + title);
      });
    });
  }
  list.addEventListener("click", event => {
    const button = event.target.closest("button[data-shift]");
    if (!button || button.disabled) return;
    const item = button.closest("li");
    const shift = Number(button.dataset.shift);
    if (shift !== -1 && shift !== 1) return;
    const peer = shift === -1 ? item.previousElementSibling : item.nextElementSibling;
    if (!peer) return;
    list.insertBefore(item, shift === -1 ? peer : peer.nextElementSibling);
    updateMoves();
    item.focus();
    status.textContent = item.querySelector("span").textContent + " moved " +
      (shift === -1 ? "up." : "down.");
  });
  updateMoves();
</script>

The controls now perform real local reordering. Boundary controls are disabled; focus goes to the moved item and visible status text explains the result. Controls begin disabled so a script failure does not leave apparently working actions. The list is not saved to a backend, and a status element is not proof of screen-reader announcements.

A mistake to watch forAdding tabindex="0" to every paragraph and wrapper, making keyboard navigation unnecessarily long.

Your turn

Check your understanding

An item can only be moved by dragging. What should you add before treating the interaction as broadly usable? Does a keyboard-only drag alternative necessarily cover every single-pointer non-drag requirement?

Read the explained answer

Provide an operable non-drag mechanism, such as Move up and Move down controls, then implement focus management and meaningful feedback for the result. Test with a keyboard and the actual input methods you support. No. Review both input paths. The example provides clickable buttons as well as keyboard activation, performs the move and leaves an inspectable focus and status result.
