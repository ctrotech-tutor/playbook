Chapter 64

Performance without folklore

Find the slow resource before adding an optimization.

2 MIN READ + PRACTICESOURCE-LINKED PRACTICEOCTOBER 2026
By the end of this chapter
  • Relate HTML loading choices to real resources
  • Report measured results with their conditions
  • Use a supplied dimensioned resource without fabricating a speed result

HTML influences resource discovery and loading. An early stylesheet link, a delayed image source, script loading attributes and image candidates can affect the page's critical work. Measure the actual page on representative conditions before prescribing changes.

Provide image dimensions and appropriate resources. Keep likely important above-the-fold media from being needlessly delayed. Lazy loading is useful when deferring a resource is appropriate; it is not a rule to apply to every image.

Test a before and an after

Record the page version, device or emulation, network conditions and measurement method. Repeat enough to recognize variation. Do not invent percentage improvements or treat one warm-cache result as a stable performance guarantee.

A fast initial response can coexist with a slow interaction. Loading less script helps only when it addresses actual work. Keep the underlying document usable while enhancements load. Review the network waterfall and interaction path together rather than optimizing a score in isolation.

Attribute hints have limited states

fetchpriority accepts high, low and auto, with Auto for missing or invalid values. It influences the relevant fetch, not a guaranteed queue position. loading uses its defined eager/lazy states; missing/invalid follows its eager default. Deferred lazy resources also have scripting-related conditions. Verify the actual resource request, decoding and layout instead of treating attribute reflection as a speed measurement.

Match a metric to the user question

LCP concerns an eligible largest-content paint candidate, CLS concerns qualifying unexpected layout shifts and INP concerns the relevant interaction responsiveness measurement. Those metrics have their own definitions, aggregation and implementation boundaries; a request count is none of them. Field data and a controlled lab run answer different questions.

Performance entries may expose limited cross-origin details without the appropriate Timing-Allow-Origin configuration. Warm caches, service workers, throttling and device work can change results. Record the conditions and repeat comparisons; no percentage or score improvement is claimed by this example.

The example

HTML / example 64
<figure>
  <img src="../assets/media/floor-plan-800.png"
       alt="Fictional schematic showing entrance, reception and reading room."
       width="800" height="450" style="max-width: 100%; height: auto"
       loading="eager" fetchpriority="high">
  <figcaption>A supplied teaching schematic, not a real entrance photograph.</figcaption>
</figure>

The resource is actually supplied and decodes to 800 by 450 pixels, so the dimensions reserve its ratio. The CSS also constrains the displayed width to the available space while retaining that ratio. This is a single likely important figure in a tiny teaching page. A high priority hint does not prove earlier delivery or an improved performance score; compare measured alternatives before generalizing.

A mistake to watch forClaiming that fetchpriority="high" on every image makes the page faster.

Your turn

Check your understanding

What evidence should accompany a claim that an HTML loading change improved performance? Does a reflected fetchPriority value of high prove that an image downloaded first?

Read the explained answer

A recorded before/after measurement under stated comparable conditions, with the tested page version and enough detail to reproduce it. Explain variability and avoid generalizing beyond the measured scenario. No. It is a hint under the fetch rules. Record actual comparable measurements, not a property value presented as a performance result.
