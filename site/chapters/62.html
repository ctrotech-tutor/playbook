Chapter 62

Keyboard and focus review

Follow the task without touching the mouse.

2 MIN READ + PRACTICESOURCE-LINKED PRACTICEOCTOBER 2026
By the end of this chapter
  • Run a task-based keyboard check
  • Plan focus after dynamic changes
  • Execute removal/restoration with predictable focus destinations

Begin at the top of the page and use Tab, Shift+Tab, Enter, Space and the keys appropriate to each native control. Confirm that every needed action is reachable, the order is sensible and focus remains visible.

Do not require hover to reveal the only route to an action. A control that appears on pointer hover should have an equivalent usable focus or interaction path. Keep focus indications strong enough to locate rather than removing outlines without a replacement.

Check transitions, not just tab stops

Open and close a dialog. Submit an invalid form. Remove a focused list item. Load more results. These transitions need deliberate focus and feedback behavior. Moving focus on every update can be as disruptive as losing it.

A disabled control and an aria-disabled control do not automatically behave the same way. ARIA communicates semantics but does not implement all interaction restrictions. Choose the appropriate element/state and test the actual behavior.

Record the browser, operating system and assistive technology used. A successful keyboard pass in one environment is useful evidence, not a claim about all combinations.

Focus must survive the state transition

A predictable focus order is about usable relationships, not merely counting Tab presses. If a focused row disappears, select the next or previous relevant action, or a meaningful heading when the list is empty. Restore should also have a deliberate destination. The working example makes that policy inspectable.

Sequential focusability, programmatic focus, disabled state and aria-disabled remain different. A custom aria-disabled action still needs its click/keyboard suppression implemented. A sticky overlay can obscure the focused item even when the item is technically focused; review Focus Not Obscured alongside Focus Order and Focus Visible.

Native control keys and platform tab preferences can vary. Record actual key actions and results, not a universal assumption that every native widget exposes exactly the same tab stops. Focus tests should cover pointer-triggered transitions too, and never claim OS screen-reader output from document.activeElement alone.

The example

HTML + JavaScript / example 62
<!doctype html>
<html lang="en">
<head>
  <meta charset="utf-8">
  <title>Local reading-list focus review</title>
<style>
  .skip-link { position: absolute; left: .5rem; top: .5rem;
    transform: translateY(-180%); background: white; color: black;
    padding: .5rem; z-index: 2; }
  .skip-link:focus { transform: none; }
  a:focus-visible, button:focus-visible, [tabindex]:focus-visible {
    outline: 3px solid #163fc2; outline-offset: 3px;
  }
</style>
</head>
<body>
<a href="#keyboard-main" class="skip-link">Skip to main content</a>
<main id="keyboard-main" tabindex="-1">
  <h1 id="list-heading" tabindex="-1">Fictional reading list</h1>
  <ul id="removable-list">
    <li><span>Local histories</span> <button type="button" disabled>Remove Local histories</button></li>
    <li><span>Poetry</span> <button type="button" disabled>Remove Poetry</button></li>
    <li><span>Fiction</span> <button type="button" disabled>Remove Fiction</button></li>
  </ul>
  <p id="remove-status" role="status">Changes stay in this page only.</p>
  <button id="restore-list" type="button" disabled>Restore initial titles</button>
</main>
<script>
  const list = document.getElementById("removable-list");
  const note = document.getElementById("remove-status");
  const heading = document.getElementById("list-heading");
  function enableItems() {
    list.querySelectorAll("button").forEach(button => button.disabled = false);
  }
  list.addEventListener("click", event => {
    if (!(event.target instanceof Element)) return;
    const button = event.target.closest("button");
    if (!button || button.disabled) return;
    const item = button.closest("li");
    const next = item.nextElementSibling || item.previousElementSibling;
    const destination = next ? next.querySelector("button") : heading;
    const title = item.querySelector("span").textContent;
    item.remove();
    destination.focus();
    note.textContent = title + " removed from this local list.";
  });
  const restore = document.getElementById("restore-list");
  restore.addEventListener("click", () => {
    list.replaceChildren();
    for (const title of ["Local histories", "Poetry", "Fiction"]) {
      const item = document.createElement("li");
      const text = document.createElement("span");
      const button = document.createElement("button");
      text.textContent = title;
      button.type = "button";
      button.textContent = "Remove " + title;
      item.append(text, " ", button);
      list.append(item);
    }
    heading.focus();
    note.textContent = "The initial teaching list was restored.";
  });
  enableItems();
  restore.disabled = false;
</script>
</body>
</html>

The skip link has a supplied focus-visible style, and removal now performs the actual local action. Focus moves to the next item, otherwise the previous item, otherwise the heading. Restore rebuilds the teaching list safely and returns focus to its heading. This is not saved to a server; status announcements and focus visibility still need actual OS AT and user review.

A mistake to watch forSetting a positive tabindex sequence to match a visual layout instead of fixing the source order.

Your turn

Check your understanding

After deleting the focused row in a list, where should focus go? What should happen when the final item is removed in this example?

Read the explained answer

There is no universal target. Choose a predictable nearby control or a relevant list heading based on the task, then test the behavior. Do not let focus disappear into the document body accidentally. The meaningful list heading receives focus. The visible result explains the local removal; actual assistive-technology feedback must still be checked.
