Chapter 61

Accessibility starts in the markup

Semantic HTML helps, but it does not certify the whole experience.

3 MIN READ + PRACTICESOURCE-LINKED PRACTICEOCTOBER 2026
By the end of this chapter
  • Use native semantics with accurate names
  • Separate automated checks from accessibility conformance
  • Test the actual local filter across success, empty and reset states

Use native elements that fit the task, then review the name, role, state and behavior actually exposed to users. A button needs an understandable name and an operable action. A heading needs a useful position in the document hierarchy. A table needs its data relationships.

ARIA can supplement semantics where needed. It can also introduce wrong or conflicting information. Follow ARIA in HTML restrictions rather than adding roles to every element. Prefer an existing visible label through a native label relationship or a suitable reference before inventing an unrelated hidden name.

Review the entire task

A successful automated scan does not demonstrate WCAG conformance. Test keyboard operation, visible focus, text alternatives, error correction, zoom, reflow and appropriate assistive-technology behavior. Include the actual data and content states, not just a polished empty page.

WCAG describes requirements at the level of the delivered experience. HTML-AAM, AccName, WAI-ARIA and ARIA in HTML help answer more specific mapping and authoring questions. This edition links to them but has not completed an independent accessibility audit. Record that limitation instead of turning a few semantic examples into a certification badge.

A usable name must still describe the visible task

Accessible-name computation follows its rules, including labelledby references, aria-label, host-language labels and other context-specific sources. An aria-label can override a useful visible label in relevant cases. That is not automatically an improvement: preserve the visible label text in the accessible name where the applicable Label in Name requirement calls for it.

ARIA roles/states do not implement a custom widget's keyboard behavior, validation or permission checks. Adding role="button" to a span does not turn it into a native button. Use ARIA in HTML to check permitted overrides, and HTML-AAM/AccName for mapping/name questions rather than equating a DOM attribute with an OS accessibility result.

Follow one task across its states

For the supplied filter, test label/name, query entry, Enter activation, matching results, no matches, reset and failed scripting. Verify status communication with the actual assistive technology. Do not move focus to the status after every query merely to force an announcement.

Record zoom/reflow, contrast, visible focus, target sizing, error recovery and text alternatives as separate applicable checks. WCAG 2.2 has requirements beyond a clean semantic snippet; no automated result or role query closes that review.

The example

HTML + JavaScript / example 61
<section aria-labelledby="catalogue-heading">
  <h2 id="catalogue-heading">Supplied fictional titles</h2>
  <form id="local-filter">
    <label for="catalogue-query">Filter supplied titles</label>
    <input id="catalogue-query" name="q" type="search" disabled>
    <button type="submit" disabled>Filter titles</button>
    <button type="reset" disabled>Show all titles</button>
  </form>
  <p id="catalogue-result" role="status">All three teaching titles are listed below.</p>
  <ul id="catalogue-list">
    <li>Local histories</li>
    <li>Poetry</li>
    <li>Fiction</li>
  </ul>
  <p><a href="#catalogue-list">Browse the supplied list</a></p>
</section>
<script src="../assets/catalogue-demo.js" defer></script>
<noscript><p>Filtering needs JavaScript; the supplied list remains readable.</p></noscript>

The visible label, native controls and actual local filter support a complete small task. Enter submits, reset restores the three titles and a no-match query gets a visible status. No live catalogue or availability service is implied. The external script is supplied; the editor blocks it, so the standalone example is the enhancement test target. role=status is not proof that every assistive-technology combination announces the update.

A mistake to watch forAdding an aria-label that contradicts the visible wording, or describing role-based automated tests as a complete accessibility review.

Your turn

Check your understanding

A scanner reports no issues. What should you do before claiming that the search experience is accessible? Does overriding a visible label with an unrelated aria-label necessarily improve usability?

Read the explained answer

Complete the relevant manual and assistive-technology checks across the actual task and states, assess applicable WCAG requirements, and document results and limitations. A scanner result is one piece of evidence. No. Preserve task meaning and review name computation, permitted ARIA and Label in Name. Test the actual task and assistive-technology output, not just the attribute.
