Chapter 39

Menus and longer text

Choose the control that fits the number and kind of answers.

3 MIN READ + PRACTICESOURCE-LINKED PRACTICEOCTOBER 2026
By the end of this chapter
  • Use select, datalist and textarea intentionally
  • Keep a native baseline for newer select customization
  • Distinguish selected option content from its label metadata

select represents a choice among option elements, with optgroup available to group related choices. A native select carries behavior that a custom visual menu would otherwise need to recreate. Use a visible label and make any initial prompt consistent with required-selection rules.

textarea is for multiline text. Its initial value comes from its text content, not a value attribute. A datalist can supply suggestions for an associated input, but suggestions do not normally restrict the user to the listed values.

Customizable selects need extra review

The Living Standard includes selectedcontent and newer customizable-select behavior. Their permitted structure and browser support need separate attention. Keep a conventional select usable as the baseline rather than assuming a decorative demonstration proves full keyboard and assistive-technology support.

multiple changes both the interface and submission expectations for a select. Do not use a multiple list solely to imitate the visual height of a different widget. Explain how to choose and how the service interprets several selected values.

A placeholder option has a defined position

For the required single-select, display-size-one context used here, the placeholder label option is the first option with an empty value and no intervening optgroup ancestor. Moving the prompt into an optgroup can change whether it meets that rule. A nonempty displayed phrase alone does not establish an allowed submitted value.

Give conventional optgroups a label. The newer model also permits a first-child legend under its rules, but that needs implementation review rather than an assumption that every native picker renders arbitrary group markup. Set explicit option values when the service needs stable keys; otherwise the option's defined text processing supplies the value.

selected initializes an option's default selected state. The current selected property can change without rewriting that attribute. In a multiple select, several selected options produce repeated entries under the same name. For a textarea, defaultValue comes from its child text, while value is the current value and uses normalized LF line breaks. wrap="hard" requires cols and can insert submission line breaks; the usual Soft state does not request that hard wrapping.

Explain selectedcontent, not just its name

In a supported customizable drop-down, the select may start with a button containing <selectedcontent></selectedcontent>. The element has no authored children: the browser clones the selected option's child content into it. An option's label attribute is not that cloned content, and the update algorithm does not use this mechanism for a multiple select.

For example, <select name="shelf"><button><selectedcontent></selectedcontent></button><option value="fiction">Fiction</option><option value="history">History</option></select> shows the intended structure; add a visible associated label in a complete form. The customizable rendering opt-in also involves CSS. Support cannot be inferred from successfully retaining an unknown element in the DOM. Keep the choice values usable in a conventional native baseline, avoid ids that become duplicate relationships when content is cloned, and test real keyboard and assistive-technology behavior.

The example

HTML / example 39
<label for="branch">Preferred branch</label>
<select id="branch" name="branch" required>
  <option value="">Choose a branch</option>
  <option value="central">Central</option>
  <option value="east">East</option>
</select>
<label for="request">What would you like to read?</label>
<textarea id="request" name="request" rows="4"></textarea>

This is a conventional select baseline. Its empty initial option works with the required single-select context shown here. Check the detailed placeholder-label rules before changing the structure.

A mistake to watch forAssuming datalist creates a strict allowed-value list or that textarea uses value like an input.

A field must accept only Central or East. Does an input with datalist enforce that restriction? Does selectedcontent mirror an option label attribute or move its original child nodes?

Read the explained answer

No. A datalist provides suggestions. Use a suitable select for this choice and validate the submitted value on the server. A client can send any value regardless of the visible controls. Neither. Its defined update clones the selected option child content, not the label attribute. A retained unknown tag alone is not proof that the browser implements those updates.
