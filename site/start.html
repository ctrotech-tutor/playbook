One useful practice loop

  1. Predict before running

    Read the objective and example. Describe the expected document relationships, submitted entries or interaction in your own words. Separate the markup rule from a styling choice.

  2. Inspect the result

    Use a complete document where a fragment needs one. Compare the source with the live DOM. Use the keyboard for interactive examples and check the console or network panel when the lesson concerns requests or loading.

  3. Answer before opening the solution

    Write a short answer and a reason. Then compare the explained answer with your reasoning, not just its vocabulary. A mismatch is a prompt to revisit the example and source, not a score.

  4. Change one requirement

    Try a longer label, a missing resource, a narrow viewport or a different control state. State what should remain true. Use fictional values, especially in forms. The book sandbox restricts resource loading and form submissions. It runs inline scripts; do not paste secrets or run code you do not trust.

Know what a source tells you

WHATWG defines HTML. MDN helps explain features and implementation support. WAI and WCAG provide accessibility guidance and requirements. A conformance checker, browser test and accessibility review answer different questions. Follow the source links and read the scope of each recorded check.

Scope of this edition

This is a published reading curriculum with captured reference inventories. It is not a completed whole-Standard behavioral reference. Independent technical, answer-key, accessibility and security reviews remain open. The PDF has selectable text, links and bookmarks, but is not a tagged accessible PDF.

Help correct the book

Report a correction with the page URL or chapter number, the passage, the expected result and a supporting source. For browser-dependent behavior, include the browser version and a small reproducible example. GitHub requires an account. Never include secrets or personal form data in a public issue.
